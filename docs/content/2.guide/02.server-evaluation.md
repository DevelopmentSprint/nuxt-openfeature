`evaluateFeatureFlag` and `getFeatureFlagContext` are auto-imported in Nitro
handlers.

```ts [server/api/checkout.post.ts]
export default defineEventHandler(async (event) => {
  const session = await requireUserSession(event) // your auth

  const context = getFeatureFlagContext(event, {
    targetingKey: session.user.id,
    traits: { plan: session.user.plan }
  })

  const useNewFlow = await evaluateFeatureFlag('new-checkout', false, context)
  return useNewFlow ? newCheckout(event) : legacyCheckout(event)
})
```

## Value types

The default value's type selects the OpenFeature resolver:

| Default | Resolver |
| --- | --- |
| `false` | boolean |
| `'control'` | string |
| `10` | number |
| `{}` | object |

On error, the default is returned.

## Any flag, not only public ones

Server-side evaluation can read any flag your providers know about.
`publicFlags` only gates the batch endpoint that the client composables call.

## Trusted context

`getFeatureFlagContext` merges the browser's context with the context you pass.
Your `targetingKey` and traits override the client's values.

::warning
Browser context is untrusted input. Base access decisions on your server
session, and pass trusted identity through `getFeatureFlagContext`. See
[Context and targeting](/guide/context-and-targeting).
::
