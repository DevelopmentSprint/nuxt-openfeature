The module sends client context to server evaluation endpoints using compressed headers with a SHA-256 checksum.

## Request isolation

The server reads targeting context from the current request and passes it directly to each OpenFeature evaluation. It does not set user context on the shared OpenFeature client or global API, avoiding shared user state across concurrent server requests. For server-side rendering, pass context derived from the current request to the server evaluation helpers; the browser context plugin runs only on the client.

The checksum detects payload corruption, but it is not a signature and does not authenticate the user. Treat browser-supplied targeting keys and traits as untrusted input; use your authenticated server session for trusted identity and authorization decisions.

## How context is built

The client plugin (`openfeature-context.client.ts`) builds context with:

- `targetingKey`: current authenticated user id (when available)
- `traits.locale`: `navigator.language`
- `traits.timezone`: browser timezone
- `traits.platform`: browser platform string
- `traits.userAgent`: browser user agent
- user traits when authenticated (`userId`, `email`, `emailVerified`, `userCreatedAt`)

## Signed-in user

The module reads the signed-in user from Nuxt state under the key `auth-user`. Your app owns this state: set it after login and clear it on logout.

```ts
type AuthUser = {
  id: string
  email: string
  emailVerifiedAt: Date | null
  createdAt: Date | string
}

const user = useState<AuthUser | null>('auth-user', () => null)

// After login
user.value = {
  id: session.user.id,
  email: session.user.email,
  emailVerifiedAt: session.user.emailVerifiedAt,
  createdAt: session.user.createdAt
}

// On logout
user.value = null
```

When `auth-user` holds a user, the client plugin:

| Context field | Value |
| --- | --- |
| `targetingKey` | `id` |
| `traits.userId` | `id` |
| `traits.email` | `email` |
| `traits.emailVerified` | `true` when `emailVerifiedAt` is not `null` |
| `traits.userCreatedAt` | `createdAt` as an ISO string |

`useFeatureFlag` also includes the user's `id` in its query key, so changing or clearing `auth-user` refetches flags for the new identity. When the state is `null` or unset, flags are evaluated with browser context only.

This state comes from the browser, so the server cannot trust it (see [Request Isolation](#request-isolation)).

## Header format

| Header | Purpose |
| --- | --- |
| `x-of-ctx-enc` | Encoding marker (`json+gzip+base64url`) |
| `x-of-ctx-sha256` | SHA-256 hash of canonical JSON payload |
| `x-of-ctx` | Single-header payload when size allows |
| `x-of-ctx-chunks` | Number of chunks when payload is split |
| `x-of-ctx-0 ... x-of-ctx-N` | Chunk payload segments |

## Size and safety limits

| Limit | Value | Source |
| --- | --- | --- |
| Single header threshold | `4096` chars | client encoder |
| Chunk size | `2048` chars | client + server |
| Maximum chunks | `32` | client + server |
| Maximum encoded size accepted | `65536` chars | server decoder |

If payload is too large, the client skips sending context headers and evaluation proceeds without context.

## Integrity rules

The server rejects the request (`400`) when:

- encoding marker is missing or invalid
- required hash is missing
- chunk metadata is invalid
- any chunk is missing
- hash does not match decoded JSON
- payload cannot be decoded or parsed

## Context merge semantics

When both client and server context are present:

- `targetingKey`: server value takes precedence
- traits: server traits overwrite matching client trait keys
- non-overlapping traits are merged

## Server-side context override example

```ts
import { getFeatureFlagContext } from '#imports'

export default defineEventHandler((event) => {
  const context = getFeatureFlagContext(event, {
    targetingKey: 'internal-service-account',
    traits: {
      region: 'us-east-1',
      plan: 'enterprise'
    }
  })

  return { context }
})
```
